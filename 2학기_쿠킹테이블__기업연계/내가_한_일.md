## 문제와 선택

각 사례는 **상황 → 고민한 선택지 → 고른 것과 이유 → 결과** 순서로 적었습니다.

### 1. 영상 업로드가 서버 문 앞에서 막혔다 (413)

**상황**
앱에서 12MB 영상을 올리면 API에 닿기도 전에 Nginx가 `413 Request Entity Too Large`를 돌려줬습니다. 업로드 주소(`/api/v1/inputs`)도 일반 API 규칙(`/api/`, 본문 10MB)에 걸려 있었습니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `/api/` 전체 한도를 400MB로 올린다 | 한 줄이면 끝 | 아무 API에나 큰 요청을 보내 서버를 괴롭힐 수 있다 |
| B. API 서버가 직접 받게 Nginx 제한을 없앤다 | Nginx 설정이 단순해진다 | 큰 본문이 API 스레드를 오래 붙잡는다 |
| **C. 업로드 경로만 따로 규칙을 둔다** | 나머지 API는 작고 짧은 규칙 그대로 | 경로마다 규칙을 관리해야 한다 |

**선택: C**
Nginx는 가장 길게 일치하는 location을 고르므로, 업로드 주소에만 별도 블록을 두면 다른 API 규칙은 건드리지 않습니다. 업로드 경로는 본문 34MB(API 한도 32MiB + multipart 여유), 본문 수신 120초, **버퍼링 없이 바로 API로 전달**하도록 했습니다. 그 뒤 팀이 조각 업로드로 바꾸면서 조각 경로(`/api/v1/uploads/`)는 조각 하나 기준 20MB로 맞췄습니다.

**결과**
12MB 업로드는 Nginx를 통과하고, 40MB는 여전히 413, 다른 API는 10MB 그대로인 것을 서버 밖에서 직접 요청을 보내 확인했습니다. 이 경험 뒤로 모든 경로 규칙을 README 표(경로 · 본문 최대 · 시간 제한 · 요청 수 제한 · 용도)로 관리했습니다.

### 2. 로그인을 어느 서비스가 맡을까

**상황**
서버에는 요청 서비스(영상·작업)와 앱 서비스(기록·공유)가 따로 있었고, 둘 다 "이 요청이 누구 것인지" 알아야 했습니다. 그때까지는 시험용 헤더(`X-Owner-Id`)를 그대로 믿고 있어서, 열면 남의 기록을 바꿀 수 있는 상태였습니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 각 서비스가 카카오·구글 로그인을 직접 처리 | 서비스가 독립적 | 같은 로그인 코드가 두 벌, 키도 두 곳에 |
| B. 공유 비밀키(HS256)로 토큰을 서명 | 구현이 쉽다 | 검사하는 서비스도 비밀키를 가져서, 어느 한 곳만 털려도 토큰을 위조할 수 있다 |
| **C. 로그인 서비스 하나 + RS256 서명, 다른 서비스는 공개키(JWKS)로 검사만** | 개인키는 한 곳에만. 다른 서비스는 카카오·구글을 몰라도 된다 | 서비스가 하나 더 늘고 키 교체 절차가 필요하다 |

**선택: C**
API 담당 팀원과 토큰 약속(서명 방식, `iss`, `aud`, 수명, 이름·이메일을 넣지 않는다)을 먼저 문서로 맞추고 Spring Boot로 구현했습니다. 보안 장치는 다음과 같습니다.

- 갱신 토큰은 쓸 때마다 새로 주고, **이미 쓴 토큰이 다시 오면 그 로그인 전체를 끊는다**(복사본을 가진 사람이 있다는 뜻).
- DB에는 갱신 토큰의 해시만 저장한다.
- 로그인 시작마다 state와 PKCE를 써서 로그인 위조와 code 가로채기를 막는다.
- 로그인 후 돌아갈 주소는 `/app/` 아래만 받는다(open redirect 방지).

**결과**
시험 18개(가짜 카카오 서버로 전체 로그인 흐름 포함)를 통과했습니다. 이 서비스가 서명한 토큰을 다른 두 서비스의 운영 검사에 넣어 정상 200, 남의 자원 404, 변조 401을 확인한 뒤 배포했습니다. 나중에 네이버 로그인도 코드 구조를 바꾸지 않고 추가했습니다.

### 3. 휴대폰 앱에는 토큰을 어떻게 넘길까

**상황**
웹은 갱신 토큰을 `HttpOnly` 쿠키로 주면 됩니다. 앱은 브라우저에서 로그인한 뒤 딥링크(`cooking-record://auth`)로 앱에 돌아와야 하는데, 같은 주소를 등록한 다른 앱이 딥링크를 가로챌 수 있습니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 딥링크 주소에 토큰을 바로 싣는다 | 단순하다 | 가로챈 앱이 그대로 토큰을 쓴다 |
| **B. 딥링크에는 60초짜리 1회용 code만 싣고, 앱이 처음 만든 비밀값(verifier)과 함께 바꾼다** | code를 가로채도 verifier 없이는 쓸모가 없다 | 앱과 서버 모두 단계가 하나 늘어난다 |

**선택: B**
앱이 로그인 시작 때 verifier의 해시만 보내고, 끝나면 code + verifier를 서버에 보내 토큰을 받습니다. code는 맞든 틀리든 한 번 시도하면 지웁니다. 돌아갈 딥링크 주소도 설정한 하나와 정확히 같을 때만 받습니다.

**결과**
틀린 verifier로 시도하면 400이 나고 그 code는 진짜 앱도 다시 못 쓰는 것, 재사용·만료 code가 모두 거절되는 것을 시험으로 확인했습니다.

### 4. 백업은 "복구해 봐야" 백업이다

**상황**
DB 백업은 서버 안에만 있었습니다. 서버가 사라지거나 잘못 지워지면 백업도 같이 사라집니다. 서버는 프로젝트가 끝나면 삭제될 예정이기도 했습니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 서버 안 백업만 유지 | 추가 작업 없음 | 서버와 운명을 같이한다 |
| B. 서버 밖으로 그대로 복사 | 서버가 사라져도 남는다 | 개인정보가 담긴 DB가 평문으로 다른 곳에 놓인다 |
| **C. age로 암호화해 서버 밖에 보관 + 매주 자동 복구 연습** | 키 없이는 못 읽고, 실제로 되살아나는지 매주 확인 | 키 관리 책임이 생긴다 |

**선택: C**
서버에는 공개키만 두고 암호화만 하게 했습니다. 개인키는 운영 담당자 PC에만 있습니다. 복구 연습은 백업을 임시 DB에 되살려 표·행 수를 원본과 비교한 뒤 임시 DB를 지웁니다.

**결과**
첫 실행에서 DB 3개의 표·행 수가 모두 일치했습니다. 그런데 **한 바이트를 바꾼 파일을 넣어 보니 검사가 통과**했습니다. 파이프(`age | tar`)에서 tar의 종료 코드만 보고 있었던 것입니다. age 검사를 따로 한 번 더 하도록 고쳐, 변조 파일은 실패(exit 1)로 잡히게 했습니다. 개인정보 처리방침에도 "암호화한 백업본을 운영 담당자 PC에 같은 기간 보관"을 추가했습니다.

### 5. 원격 서버의 SSH를 고치다 잠기면 끝이다

**상황**
보안 점검에서 SSH로 들어올 수 있는 계정이 여러 개(root·DB·배포 계정)인 것을 발견했습니다. 원격 서버에서 SSH 설정을 잘못 바꾸면 **다시 들어갈 방법이 없습니다.**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 설정을 바꾸고 바로 적용 | 빠르다 | 실수하면 서버에 영영 못 들어간다 |
| B. 지금 상태로 둔다 | 위험 없음 | 공격 표면이 그대로 |
| **C. 3분 뒤 자동으로 되돌리는 예약을 먼저 걸고 적용 → 새 창으로 접속 확인 → 예약 취소** | 실수해도 3분 뒤 원래대로 돌아온다 | 절차가 조금 길다 |

**선택: C**
`systemd-run`으로 되돌리기 예약을 걸고, `sshd -t`로 문법을 확인한 뒤 적용했습니다. 새 창에서 접속이 되는 것을 본 다음에야 예약을 취소했습니다. 이후 커널 네트워크 설정을 바꿀 때도 같은 방식으로 백업·되돌리기 방법을 먼저 적고 시작했습니다.

**결과**
SSH 접속을 ubuntu 계정 하나로 제한했고, 다른 계정은 거절되는 것을 확인했습니다. 같은 점검에서 fail2ban 차단이 0건인 이유도 찾았습니다. 기본 모드는 키 로그인 시도를 실패로 세지 않아서 `aggressive` 모드로 바꿨습니다. 팀원 모두가 같은 SSAFY 출구 IP를 쓰기 때문에, 차단 기준은 팀이 서로를 막지 않도록 느슨하게 잡았습니다.

## 돌아보며

- **바꾼 설정은 저장소에 사본으로 남겼습니다.** 서버에서 고치면 저장소 `infra/`도 같이 고쳐 커밋하고, 바꾸기 전 설정은 서버에 날짜를 붙여 백업했습니다. 덕분에 다른 팀원이 바꾼 설정과 충돌해도 무엇이 달라졌는지 바로 비교할 수 있었습니다.
- **"닫혀야 할 것"까지 밖에서 확인했습니다.** `nginx -t` 통과는 시작일 뿐이라, DB·API 포트가 밖에서 닫혀 있는지까지 보는 점검 스크립트를 만들어 설정을 바꿀 때마다 돌렸습니다.
- 아쉬운 점: CI/CD는 구성안까지만 만들고 실제로 켜지 못했습니다. 변수 등록 권한이 다른 팀원에게 있었고, API 배포 방식이 늦게 정해졌기 때문입니다. 다음에는 권한과 배포 방식을 프로젝트 초반에 먼저 정하겠습니다.
